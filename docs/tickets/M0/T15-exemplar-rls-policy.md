# T15 — Golden-path exemplar: RLS policy + the canary-row test (the tenant-isolation moat)

> **Tier:** 1 (RLS is the tenant-isolation moat — a missing RLS policy is a cross-tenant data leak, a moatbreach) | **Status:** pending | **Milestone:** M0
> **Cites:** `28` §4 (golden-path exemplars) · `15_TENANT_BOUNDARIES.md` (RLS-by-tenant, the `tenant_id`-from-JWT rule) · `13_DATABASE_ARCHITECTURE.md` (the bi-temporal schema + the `assertion_view`) · `23_QUALITY_GATES.md` §3 (the RLS-introspection gate + the canary-row RLS test) · `CLAUDE.md` §7 (RLS-introspection + canary-row in the CI gate chain) · `CODING_STANDARDS.md` (E07 — no hand-written `valid_time @>`; the `assertion_view` is the only bi-temporal path) · `ADR-0003` (the self-managed Postgres + AGE — the M0 CNPG cluster from T04) · T04/T06

## Objective

Ship the **RLS golden-path exemplar** — one reviewed reference migration (a trivial multi-tenant table via Atlas, schema-as-code) + the RLS policy (the `tenant_id` scoping, the `current_setting('app.tenant_id')` from the JWT-bound session — `15` §3) + the **canary-row test** (the CI gate that introspects `pg_policies`, asserts every scoping-required table has a `tenant_id` policy, + a tenant can only see its own rows) + the **RLS-introspection gate** (the CI gate that fails if a scoping-required table lacks a `tenant_id` policy — `23` §3 + `CLAUDE.md` §7). This is the execrable form of the tenant-isolation moat: the test that catches a missing RLS policy at PR time, not at the cross-tenant-leak audit. M0 runs against the CNPG cluster T04 provisioned (the ADR-0003 cell).

## Dependencies

- **Tickets:** T04 (the CNPG cluster — the RLS exemplar runs against the M0 cell's Postgres with AGE+pgvector + RLS extensions), T06 (the CI gates — the canary-row + the RLS-introspection run in the `security-scan`/`kg-rls` workflow; needs the M0 cell reachable from CI or a CI-side testcontainer Postgres).
- **External:** Atlas (the schema-as-code migration tool from `ADR-0001`), a Postgres 16+ with RLS enabled (the M0 cell from T04, or a CI-side testcontainer identical to the cell's Postgres image — pin the same version, watchdog category 5 — the AGE-compat matrix), the `pgvector`/`AGE` extensions (T04).

## Files

- `libs/kg/migrations/atlas/0001_tenant_assertion.sql` — the Atlas migration (schema-as-code): creates a trivial multi-tenant table (e.g., `assertion` — the spine-of-truth table, `13` §2) with `id`, `tenant_id`, `valid_time`, `payload`, the `tenant_id` index + the `valid_time` index; **the migration is expand/contract-native** (`17` §4 — Atlas's HCL-declared reversible migration; the destructive contract belongs in a separate migration, not this one).
- `libs/kg/migrations/atlas/atlas.hcl` — the Atlas config (the dev-side connection to the M0 cell or the testcontainer; the migration directory's `atlas.sum` checksum; the lint config that forbids a destructive op in the same migration as an expand — the watchdog category 3 contract-spine check is augmented here).
- `libs/kg/policies/rls_assertion.sql` — the RLS policy for the `assertion` table: `ALTER TABLE assertion ENABLE ROW LEVEL SECURITY;` + `CREATE POLICY tenant_isolation ON assertion USING (tenant_id = current_setting('app.tenant_id')::uuid);` — the `current_setting('app.tenant_id')` is the JWT-bound session variable (`15` §3 — the `tenant_id` is from the JWT, never from a client request body; the watchdog catches a client-supplied `tenant_id`).
- `libs/kg/policies/rls_regression.sql` — the regression RLS check (a fixture set of rows across 3 tenants + a query under each tenant's session — the canary-row: a tenant's `SELECT` returns only its rows; a cross-tenant `SELECT` returns zero rows; a cross-tenant `UPDATE` is rejected). The "canary row" is a deliberately-provocative row that, if returned to the wrong tenant, fails the test (the row's payload is `CANARY-TENANT-LEAK-{{tenant}}`).
- `libs/kg/test/rls_canary_test.py` — the canary-row test (the CI gate): connects as tenant A, asserts A sees only A's rows + the canary row for tenant B is NOT in the result; connects as tenant B, asserts B sees only B's rows; asserts the `pg_policies` introspection has a `tenant_id` policy on `assertion`. The query path uses the `assertion_view` library (the only allowed bi-temporal path — no hand-written `valid_time @>`, `13` §3 + watchdog category 4).
- `libs/kg/test/rls_introspection.py` — the **RLS-introspection gate**: queries `pg_policies` (or `pg_class.relrules`) for every scoping-required table in the schema; fails the gate if any table lacks a `tenant_id` policy. This is the `23` §3 + `CLAUDE.md` §7 gate — the "every RLS-required table has a policy" assertion. The gate is exhaustive — it lists the scoping-required tables from the Atlas-defined schema; a new table without a policy fails the gate, even if the table's author forgot.
- `libs/kg/src/assertion_view.py` (or `.ts`/`.go` — pick the libraries/native lang per `libs/kg/`'s choice) — the `assertion_view` query library: the **only** allowed bi-temporal query path (`13` §3 — the lint bans hand-written `valid_time @>` queries; the watchdog category 4 catches the hand-written variant). The exemplar's `assertion_view` is the stub the real KG query layer fills at M1+.
- `libs/kg/README.md` — the "how to copy this exemplar" doc: the migration patterns (Atlas expand-first, the destructive-separately), the RLS policy patterns (`current_setting('app.tenant_id')` from JWT, the `USING` clause, the policy per table), the canary-row test pattern, the `assertion_view`-only-path rule.

## Acceptance criteria

- [ ] `atlas migrate apply` succeeds against the M0 cell (T04) or the CI testcontainer — the migration is reversible + expand/contract-clean (no destructive op in the same migration as an expand; the watchdog category-3 check passes).
- [ ] The RLS policy is enabled on the `assertion` table; `SELECT` under a tenant's session returns only that tenant's rows (the canary row for another tenant is NOT visible — the canary-row test).
- [ ] The **canary-row test** passes: 3 tenants × the canary row cross-tenanted; under each tenant session, only that tenant's rows (incl. its own canary) are visible; cross-tenant `UPDATE`/`DELETE` rejected by RLS.
- [ ] The **RLS-introspection gate** passes: the gate queries `pg_policies` + asserts every scoping-required table in the schema has a `tenant_id` policy — a fixture table without a policy fails the gate (the negative test).
- [ ] The `tenant_id` is sourced from `current_setting('app.tenant_id')` (the JWT-bound session variable), **never** from a client request body — `15` §3 + watchdog category 4 (a client-supplied `tenant_id` is caught).
- [ ] No hand-written `valid_time @>` query in the exemplar — the bi-temporal query uses the `assertion_view` library (`13` §3 + watchdog category 4).
- [ ] The migration is Atlas-HCL-defined + reversible (`17` §4 — Atlas's expand/contract-native; the down-migration is generated, not hand-rolled).
- [ ] The exemplar runs green through the T06 CI chain — the canary-row test + the RLS-introspection gate run in CI.
- [ ] The Postgres version is the cell's pinned version (T04 + the AGE-compat matrix — watchdog category 5; the testcontainer matches the cell image).
- [ ] The README walks the copy-pattern — the teaching surface for the KG + the RLS layer.

## Tests

- **Canary-row test (the gate):** `rls_canary_test.py` — tenant A sees only A's rows (incl. A's canary); the canary for tenant B is NOT visible to A; cross-tenant `UPDATE` rejected. The query path uses the `assertion_view` (no hand-written `valid_time @>`).
- **RLS-introspection gate:** `rls_introspection.py` — queries `pg_policies` for every scoping-required table; a fixture table without a `tenant_id` policy fails the gate (the negative test).
- **Migration reversibility test:** `atlas migrate apply` followed by `atlas migrate down` succeeds — the migration is reversible (the data-rollback is separate from the deploy-rollback per `17` §8; the Atlas `down` is the schema-rollback, the data-rollback is a separate PITR).
- **Expand/contract test:** grep-assert the migration file has no destructive op (`DROP`/`ALTER … DROP COLUMN`/`ALTER TYPE …`) in the same file as an expand (`CREATE`/`ALTER … ADD COLUMN`); the destructive contract is enforced by the Atlas lint config.
- **No-hand-written-bi-temporal test:** grep-assert no `valid_time @>` in the exemplar's query code — the `assertion_view` is the only path (the watchdog category-4 rule made a test).
- **Client-supplied-tenant_id test (negative):** a fixture query that sets `app.tenant_id` from a request body (not the JWT) is caught by the watchdog (T07) — the exemplar does NOT do this; the negative test verifies the scanner catches it if it appears.
- **Contract-gate green:** the exemplar's CI run through T06's `contract-gate` is green (the migration is a Tier-1 surface; it runs through the contract-gate's `mypy --strict`/`tsc` on the test code).

## Estimated complexity

**L — ~2 days.** The risk is the AGE-compat matrix (the testcontainer's Postgres + AGE + pgvector must match the cell — watchdog category 5) + the canary-row test's correctness (a false pass — a canary row that doesn't actually leak — is a silent failure mode) + the Atlas HCL syntax drift (verify via context7 per T09). ## Notes for the implementer

- **The exemplar runs against the M0 CNPG cluster (T04) — ADR-0003's cell.** The self-managed Postgres with AGE + pgvector + RLS is the cell T04 provisioned; the exemplar's migration + policy apply against that Postgres (or a CI testcontainer built from the same image). Do not run against an AlloyDB fixture — ADR-0003 forbids it + the watchdog category 1 catches `alloydb` in `infra/`.
- **The `tenant_id` is from the JWT, never the client request body.** `15` §3 — the gateway sets `app.tenant_id` in the session from the JWT's claim; the application code never accepts `tenant_id` from a request body. A client-supplied `tenant_id` is a watchdog category-4 hit + the security reviewer's headline check. The exemplar's RLS policy reads `current_setting('app.tenant_id')` — the session var, not a request field.
- **The `assertion_view` is the only bi-temporal query path.** `13` §3 — hand-written `valid_time @>` queries are banned (watchdog category 4); the `assertion_view` library encapsulates the bi-temporal logic. The exemplar's `assertion_view.py` is the stub; M1+ fills the real bi-temporal query. The no-hand-written-bi-temporal test asserts the rule.
- **The canary row's payload must be unmistakable.** A canary that reads `CANARY-TENANT-LEAK-tenant-B` and is visible to tenant A's `SELECT` fails the test loudly. A canary that reads `test-row-42` might be missed. The candor-floor principle applies: a leak must surface loudly, never silently. The payload's `{{tenant}}` substitution makes the leak traceable.
- **The migration is expand/contract-native.** Atlas's HCL describes the desired schema; the migration is the diff; the destructive op (a future column drop) is a **separate** migration, scheduled per the expand-then-contract cadence (`17` §4). The exemplar's `0001_tenant_assertion.sql` is expand-only (creates a table); a future "drop the deprecated column" migration is the contract side, a later PR. The Atlas lint config forbids a destructive op in the same migration as an expand.
- **The RLS-introspection gate is exhaustive.** It lists the scoping-required tables from the Atlas schema; a new table added without a policy fails the gate, even if the author forgot. This is the `23` §3 + `CLAUDE.md` §7 gate — the test that makes "every tenant table has an RLS policy" a CI invariant, not a review-checklist item. A reviewer's "I think I checked them all" is not a gate; the introspection is.
- **The contract-gate applies to the migration tier too.** A migration is a Tier-1 surface (it touches the data-spine); the contract-gate's `mypy --strict`/`tsc` runs on the test code; the `buf breaking` runs on the contract package (the migration doesn't directly touch the contracts, but the `assertion` table is the spine-of-truth that the contracts describe — the alignment is reviewed at the Contract-spine lens).
- **The AGE-compat matrix is a watchdog category-5 concern.** The testcontainer's Postgres version + AGE version + pgvector version must match the cell T04 provisions. A testcontainer running Postgres 17 against a cell running Postgres 16 is a category-5 hit (a Postgres major-version skew without an AGE-compat cite). The exemplar pins the testcontainer image to the cell's, with a comment pointing to T04.
- **The exemplar is Tier 1 because RLS is the tenant-isolation moat.** A cross-tenant data leak is the most consequential defect a multi-tenant SaaS can have — it's the reputation-destroying, regulatory, lose-every-customer kind. The canary-row test + the introspection gate are the gates that make RLS a CI invariant rather than a "we promise we checked" review item. Review at the full panel: the Security lens is the headline, but Correctness (the test catches the leak) + Contract-spine (the schema is the contract's mirror) + Candor-floor (the gate is honest) all apply.
